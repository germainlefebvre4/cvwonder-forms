## Context

Greenfield application: the repository currently has no `src/`, no `package.json`, only `AGENTS.md`, a vendored JSON Schema at `schemas/cvwonder.v0.10.1.json`, and OpenSpec scaffolding. See `proposal.md` for motivation. Chosen stack (fixed, not up for debate in this design): React 19 (minimum), Vite, Zustand, Radix UI + Tailwind CSS.

The vendored schema is JSON Schema draft-07. Its `required` arrays vary by nesting level (only `person.name` is mandatory for the whole document), and it contains an `anyOf`-with-empty-string pattern on `person.email` and `person.site` (empty string OR a formatted string) that needs explicit handling wherever the schema is walked.

## Goals / Non-Goals

**Goals:**
- One vendored schema file drives both form rendering (`cv-form-editing`) and validation (`cv-schema-validation`), so upgrading the schema file is the intended path for supporting a future CV Wonder schema version.
- Keep the app fully static and client-side: no backend, no network dependency for any capability in this change.

**Non-Goals:**
- Managing actual image files (profile photo, logos, badges). Path-shaped fields (`person.depiction`, `career[].companyLogo`, `education[].schoolLogo`, `certifications[].badge`) are plain text inputs; the app never reads, previews, or writes image files.
- Byte-for-byte YAML round-trip fidelity (preserving original comments/formatting/key order of an imported file). Import is read-once into the document model; export re-serializes from that model.
- Supporting multiple/older CV Wonder schema versions simultaneously. One vendored schema version is active at a time.

## Decisions

### Schema-driven form renderer, not a hardcoded form or an off-the-shelf JSON-Schema-form library
A small in-house renderer walks `schemas/cvwonder.v0.10.1.json` and maps each node to a Radix/Tailwind field component, keyed by JSON Schema `type` plus a few recognized shapes (object → section/fieldset, array of objects → repeatable group, array of strings → repeatable text list, integer with `minimum`/`maximum` → bounded numeric control, the `anyOf`-empty-or-format pattern → single text field with conditional format validation).

Alternatives considered:
- **Hardcoded per-section form components**: faster to build initially and easier to restyle by hand, but every future schema change requires code changes, and validation logic would live separately from rendering logic (two sources of truth to keep in sync). Rejected because it contradicts the "dynamically generated from schema" goal and doubles the maintenance surface when the schema evolves.
- **Off-the-shelf JSON-Schema-driven form library** (e.g. react-jsonschema-form): gets generic rendering for free, but is difficult to restyle to the intended Radix/Tailwind look without fighting the library's own theming layer, and still needs custom handling for the `anyOf`-empty-or-format pattern. Rejected in favor of full control over markup and styling.

### `ajv` as the validator, driven directly by the vendored schema
`ajv` consumes the vendored JSON Schema (draft-07) as-is, so there is no second, hand-maintained validation schema (e.g. a parallel `zod` schema) that could drift from `schemas/cvwonder.v0.10.1.json` over time.

Alternatives considered:
- **Hand-written `zod` schema mirroring the JSON Schema**: would fit typical React form-library ecosystems more natively, but duplicates the shape of the vendored schema and requires manual updates in lockstep with any schema upgrade. Rejected to preserve a single source of truth.

### CV document lives in a single Zustand store; form fields read/write slices of it directly
No separate form-state library (e.g. react-hook-form) sits between the fields and the store: schema-driven fields bind straight to a path in the Zustand-held document, and validation runs against that same document. Field-level widgets are plain controlled components generated by the renderer, not registered with a separate form-state layer.

### YAML handling
Import parses file contents to the in-memory document shape consumed by the store and by `ajv`; export serializes that same shape back to YAML. Both directions are pure client-side operations (`FileReader`/`<input type="file">` for import, a generated `Blob` + download link for export) with no server round-trip, satisfying `cv-yaml-file-io`.

### Persistence, i18n, and theme are cross-cutting, not tied to the CV document shape
- `app-persistence`: a Zustand persistence layer mirrors the CV document store to `localStorage` on every change; it is transparent to the rest of the app (rehydrates on load, no explicit save action).
- `app-i18n`: interface strings (labels, buttons, validation messages) are looked up through a translation layer; the selected language is a small separate piece of persisted UI state, distinct from the CV document itself (the CV's own content is whatever language the user types).
- `app-theme`: light/dark selection is a small separate piece of persisted UI state driving Tailwind's dark-mode styling; it does not touch the CV document store.

## Risks / Trade-offs

- **Schema walker complexity** → the `anyOf`-empty-or-format pattern (and any other irregular shape a future schema version introduces) requires explicit, tested handling in the walker, or the "swap the file, form adapts" promise breaks silently. Mitigation: cover this pattern explicitly in `cv-form-editing` scenarios/tests, and treat any new irregular pattern encountered later as a walker change, not a one-off field override.
- **Custom renderer takes more upfront effort than hardcoded sections or a ready-made library** → accepted trade-off; the "swap the schema file" maintenance benefit is the reason this change exists.
- **No structured date fields** → `dates`/`duration` properties are unconstrained strings in the schema; rendering them as plain text (matching the schema) is simplest and avoids inventing a date format the schema does not require, at the cost of no date-specific input assistance.
